# Week 1 Journal — Gateway & Rate-Limiting Core

**Workstream:** Gateway and rate-limiting logic

## Objective

Build the smallest useful version of the API Gateway: a reverse proxy that forwards requests to a target API and returns HTTP 429 once a per-client request budget is exhausted — no persistence, no dashboard, single naive algorithm.

## Setup

- Generated project via Spring Initializr: Spring Boot (parent 4.1.0), Java 17, Maven
- Dependencies: `spring-cloud-starter-gateway-server-webmvc`, `spring-boot-devtools`, `lombok`, `spring-boot-starter-test`
- Spring Cloud version: `2025.1.2`

## Work Completed

1. **Reverse proxy route** — configured a route in `application.properties` forwarding `/test/**` to `https://httpbin.org`, with `RewritePath` stripping the `/test` prefix before forwarding.
2. **Verified end-to-end forwarding** — confirmed via `curl.exe http://localhost:8080/test/get` that the gateway correctly proxies to httpbin and relays the JSON response back unmodified.
3. **Naive rate limiter** — implemented `RateLimitFilter` (a `HttpFilter` bean) using an in-memory `AtomicInteger` counter. First 5 requests to `/test/**` are forwarded; the 6th onward is rejected with `429 Too Many Requests` and a `Retry-After` header, without reaching the origin.
4. **Verified rejection behaviour** — fired 6+ sequential requests via curl and confirmed requests 1–5 return httpbin's JSON and request 6+ returns the rate-limit rejection message.

## Issues Faced and Resolved

- **404 on all routes initially.** Root cause: `spring-cloud-starter-gateway-server-webmvc` (the newer MVC-flavoured gateway) uses the property prefix `spring.cloud.gateway.server.webmvc.routes[...]`, not the classic `spring.cloud.gateway.routes[...]` used in most tutorials (which apply to the reactive/Netty gateway) or the deprecated `spring.cloud.gateway.mvc.routes[...]` (older MVC gateway, deprecated as of Spring Cloud 2025.0.0). Fixed by updating the property prefix; confirmed Tomcat starting was correct behaviour for this dependency, not a bug.
- **PowerShell's `curl` alias** (actually `Invoke-WebRequest`) threw parsing errors and script-execution warnings on plain-text responses. Resolved by using `curl.exe` explicitly to invoke real curl.

## Known Limitations (by design, to be addressed Week 2)

- **Counter is global, not per-client** — all callers currently share the same 5-request budget.
- **Counter never refills** — once exhausted, the gateway stays locked until restart (a quota, not a rate limit).
- **No distributed correctness** — this won't hold up with multiple gateway instances, which is the actual engineering problem the project is meant to solve.

# Week 2 Journal — Redis-Backed Distributed Rate Limiting

**Workstream:** Gateway and rate-limiting logic

## Objective

Replace the Week 1 naive in-memory quota with a real distributed rate limiter: per-client token-bucket enforcement backed by Redis via Bucket4j, correct under concurrent access and capable of refilling over time rather than locking permanently once exhausted.

## Setup

* Added Redis locally via Docker: `docker run -d --name redis-gateway -p 6379:6379 redis`
* Added dependencies to `pom.xml`: `bucket4j_jdk17-core` (8.19.0), `bucket4j_jdk17-jedis` (8.19.0), `redis.clients:jedis` (5.2.0)

## Work Completed

1. **Redis connection config** — added `RedisConfig.java`, a `@Configuration` class exposing two beans: a `JedisPool` connected to `localhost:6379`, and a `ProxyManager<byte[]>` built via `Bucket4jJedis.casBasedBuilder(jedisPool).build()`.
2. **Rewrote `RateLimitFilter`** — replaced the Week 1 `AtomicInteger` counter with a real Bucket4j-managed bucket. Requests to `/test/**` are now keyed per client as `"test-api:" + request.getRemoteAddr()` and checked against a Redis-backed bucket via `proxyManager.builder().build(key, configSupplier)` and `bucket.tryConsume(1)`.
3. **Token-bucket refill logic** — configured via `Bandwidth.builder().capacity(5).refillGreedy(5, Duration.ofSeconds(20)).build()`. Capacity 5, refilling 5 tokens every 20 seconds, replacing the Week 1 quota-that-never-resets behaviour.
4. **Verified rejection under burst load** — fired 8 requests back-to-back via `1..8 | ForEach-Object { curl.exe http://localhost:8080/test/get }`; confirmed 5 succeed and the remainder return 429 with the rate-limit message.
5. **Verified refill behaviour** — after waiting ~20 seconds post-rejection, confirmed a subsequent request succeeds again, proving the bucket is a genuine rate limiter and not a one-time quota.

## Issues Faced and Resolved

* **Wrong Maven coordinates initially** — `com.bucket4j:bucket4j_jdk17-redis` is an umbrella/parent module on Maven Central, not a usable dependency directly, and version `8.10.1` doesn't exist for it. Fixed by depending on `bucket4j_jdk17-core` and `bucket4j_jdk17-jedis` directly at version `8.19.0`.
* **Outdated builder API** — initial code used `JedisBasedProxyManager.builderFor(jedisPool)`, which is the old-style Bucket4j API. In 8.19.0 the correct entry point is `Bucket4jJedis.casBasedBuilder(jedisPool)`. Also had a type mismatch: the Jedis-based proxy manager returns `ProxyManager<byte[]>`, not `ProxyManager<String>` — keys must be converted to bytes explicitly.
* **`redis.clients.jedis` package not found at compile time** despite `bucket4j_jdk17-jedis` being present — the Jedis client wasn't pulled in transitively as expected. Fixed by adding `redis.clients:jedis:5.2.0` as an explicit dependency.
* **Port 8080 already in use on restart** — a previous run (likely left alive by `spring-boot-devtools` auto-restart) hadn't released the port. Resolved by killing the stale process via `netstat -ano | findstr :8080` + `taskkill /PID <pid> /F`.
* **`JedisConnectionException: Failed to connect to localhost:6379`** — Docker Desktop's background engine wasn't running (container itself was fine once the engine was up). Distinguished this from an actual Redis-down scenario the app should eventually handle gracefully (see Known Limitations).
* **Rate limiter appeared not to trigger correctly during manual testing** — root cause was stale bucket state in Redis. Bucket4j only applies the `BucketConfiguration` supplier the first time a bucket is created for a given key; once a bucket exists in Redis, later config changes (e.g. changing refill window) are silently ignored until the key is cleared. Fixed by running `docker exec -it redis-gateway redis-cli FLUSHALL` whenever bucket rules change during testing. This is a genuine gotcha worth remembering for future test runs and for the eventual automated test suite.

## Known Limitations (by design, to be addressed Week 3)

* Client identity is just IP address (`request.getRemoteAddr()`) — no real API key or user identity yet, since registration/auth belongs to the persistence workstream.
* Target API and limit are hardcoded (`"test-api"`, fixed 5/20s bucket) — not yet driven by a per-user API registration record.
* No handling for Redis being unreachable — currently surfaces as an unhandled 500 (`JedisConnectionException`) rather than an explicit fail-open or fail-closed policy, which the proposal calls out as a required design decision.
* Only token-bucket algorithm implemented — sliding window (the second required algorithm) not yet built.
* No automated test proving correctness under concurrent load — all verification so far has been manual, sequential `curl` calls, which doesn't actually exercise the race-condition risk the project is meant to address.
* No verification yet that two gateway instances sharing the same Redis enforce a single correct shared limit — this is the project's core distributed-correctness claim and remains unproven.

# **Week 3 Journal — Concurrency Proof, Fail-Open, Sliding Window, Multi-Instance Validation**

**Workstream:** Gateway and rate-limiting logic

## **Objective**

Prove the project's core engineering claims with automated tests instead of manual `curl` checks: correctness under real concurrent load (proposal §6.1, primary evaluation metric), resilience when Redis is unavailable (§5.1, §10), a second selectable rate-limiting algorithm (§9.2), and correctness across multiple gateway instances sharing one Redis (§5.1, the project's central distributed-systems claim). Also produced a first latency measurement (§6.2).

## **Setup**

- Added dependencies to `pom.xml`:
  - `org.testcontainers:junit-jupiter:1.20.4`
  - `org.testcontainers:testcontainers:1.20.4`
  - Added the Testcontainers BOM in `dependencyManagement` to keep versions aligned.
- Created `src/test/resources/docker-java.properties` because the `test/resources` folder did not exist by default and had to be created manually.

## **Work Completed**

1. **Automated concurrency test** — Created `RateLimitConcurrencyTest.java` using Testcontainers to spin up a throwaway real Redis container for each test run, independent of the manually managed development Redis container. The test fires **200 requests from 20 concurrent threads** using `ExecutorService` and `CountDownLatch` against a bucket configured with `capacity(20)`. The test asserts that the admitted count is within approximately 2% of 20. Result: **exactly 20/200 requests were admitted**, proving that Bucket4j's Redis-backed atomic counting works under genuine concurrent access, not just sequential requests. This directly satisfies the proposal's primary evaluation metric (§6.1).

2. **Fail-open policy implemented** — Wrapped the Redis/Bucket4j call in `RateLimitFilter` inside a `try/catch`. If Redis becomes unavailable, a warning is logged and the request is allowed through instead of the gateway returning an unhandled `500` error. The decision was to use **fail-open** because a Redis outage causing 100% gateway downtime would be worse than temporarily allowing unprotected traffic. This was verified by stopping the Redis container during runtime, confirming that requests still succeeded with a warning logged, then restarting Redis and confirming that normal `429` enforcement resumed automatically without restarting the application.

3. **ApiLimitProvider seam introduced** — Added an `ApiLimitProvider` interface with `getLimitFor(apiId) -> ApiLimitConfig` and a placeholder `InMemoryApiLimitProvider` backed by a hardcoded map. This replaces the previous hardcoded configuration constant in `RateLimitFilter`. Once the persistence workstream provides a registered-APIs table, a new implementation can read the configuration from PostgreSQL without requiring changes to `RateLimitFilter`. The `apiId` is currently derived from the URL path prefix (`/test/**` → `test-api`, `/demo/**` → `demo-api`) as a temporary stand-in for the API-key-based lookup that will be added with authentication.

4. **Sliding window added as a second algorithm** — Added a `RateLimitAlgorithm` enum with `TOKEN_BUCKET` and `SLIDING_WINDOW` options and extended `ApiLimitConfig` to store the selected algorithm. `RateLimitFilter` now branches based on the configured algorithm:
   - `TOKEN_BUCKET` uses Bucket4j's `refillGreedy`.
   - `SLIDING_WINDOW` uses `refillIntervally`, where the capacity resets fully at fixed intervals instead of gradually refilling.
   
   Added a second gateway route (`/demo/**`) so both algorithms can be independently reached and tested. Verified that both routes correctly allow **5 requests before rejecting subsequent requests**.

5. **Multi-instance validation** — Ran two gateway instances simultaneously on ports `8080` and `8081`, both connected to the same Redis instance. A PowerShell script alternated requests between the two ports for the same client identity and recorded the results by port and status code. Result: **6 total successful requests across both instances, not 10**, followed by consistent `429` responses from request 7 onward on both ports. This provides direct evidence that both gateway instances share the same Redis-backed counter instead of maintaining separate per-instance budgets.

6. **Latency benchmark** — Temporarily increased the `test-api` limit to `1000` to prevent rate limiting from affecting the benchmark. Measured 20 direct requests to httpbin and 20 requests through the gateway using persistent connections on both sides. Result: approximately **26.5 ms of additional latency**, which is within the proposal's target of **≤50 ms p95 overhead (§6.2)**. The limit was reverted to `5` immediately after the benchmark.

## **Issues Faced and Resolved**

- **Testcontainers could not find a valid Docker environment** even though `docker ps` worked correctly from PowerShell. The root cause was that Docker Desktop's engine had not finished starting.

- **Persistent `BadRequestException (Status 400)` from Testcontainers** even after Docker Desktop was running. The issue was a compatibility problem between recent Docker Desktop versions using Docker Engine API `v1.44+` and the Docker client bundled with Testcontainers `1.20.4`. The first attempted fix using the `DOCKER_API_VERSION` environment variable did not work because this feature is not implemented in that Testcontainers version. The working fix was creating `docker-java.properties` under `src/test/resources` with:
  `api.version=1.44`
  
  A full project rebuild was then required so Maven copied the file into `target/test-classes`.

- **Sliding-window route rejected all 8 requests immediately** instead of allowing the first 5. The root cause was the same stale-bucket-state issue encountered in Week 2: an old bucket key was still present in Redis from an earlier test run. This was resolved by running `redis-cli FLUSHALL` again.

- **Initial latency benchmark produced a negative result**, making the gateway appear approximately 760 ms faster than the direct request. The issue was caused by `curl.exe` spawning a fresh process and performing a complete TLS handshake for every request, while the long-running gateway reused a persistent outbound connection. This compared cold connections against a warm connection rather than measuring actual gateway overhead. The benchmark was corrected by using persistent connections on both the direct and gateway sides.

### Work Completed

**1. Real Client IP Identification Behind Cloudflare**

Identified and resolved an issue where requests deployed on Render were being rate-limited using Cloudflare edge server IP addresses instead of the actual client IP. This caused requests from the same client to be distributed across multiple rate-limit buckets.

Updated the gateway to support extracting the real client IP from the `CF-Connecting-IP` header. Added a configurable setting that is disabled by default to avoid trusting spoofable headers in environments that do not use Cloudflare. Verified that the same client is rate-limited consistently, different clients receive separate rate-limit budgets, and logs record the real client IP.

**2. Readable Gateway URLs**

Enhanced gateway URL readability by supporting client-defined names in the request path instead of relying exclusively on numeric identifiers.

For example, a request can use `/weatherhello/forecast` instead of `/g/4/forecast`, making gateway URLs easier to understand and identify without requiring separate DNS configuration.

**3. UptimeRobot Integration**

Configured UptimeRobot to periodically ping the deployed API Gateway website to monitor availability. This helps keep the Render free-tier instance active through periodic requests, reducing interruptions caused by inactivity-related spin-downs, and provides visibility into website downtime.

### Outcome

Improved client identification and rate-limit enforcement behind Cloudflare, introduced more readable gateway URLs, and added external uptime monitoring for the deployed application. These changes strengthen the gateway's behavior in the production environment and improve the accessibility and availability of the hosted service.
