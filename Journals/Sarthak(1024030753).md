# Sarthak Jagota (1024030753) — API Gateway Project Journal

## Week 1

**Work Done:**

- Set up iteration one of the self-service rate-limiting API gateway using Spring Boot and Spring Cloud Gateway, with Redis-backed token-bucket rate limiting via Bucket4j, PostgreSQL persistence and JWT authentication.
- Ran the full system locally with Docker Compose (gateway, PostgreSQL, Redis and an nginx test origin).
- Fixed a startup failure (`CompatibilityNotMetException`) caused by mismatched Spring Boot and Spring Cloud versions by upgrading Spring Boot to 3.5.3 after checking the compatibility matrix and Maven Central.
- Fixed a silent proxy bug where the origin received the full `/proxy/{apiKey}/...` path: the path-stripping filter ran after route resolution, so it was wrapped in an `OrderedGatewayFilter` with `HIGHEST_PRECEDENCE`.
- Strengthened the integration test so the test origin asserts the exact path it receives, instead of accepting any path.
- Moved the API key out of the URL path into an `X-Api-Key` header, so keys no longer end up in access logs, browser history or proxy logs; verified that the old URL-based route now returns 404.

**Outcome:**

A working reverse proxy with Redis-backed rate limiting, running locally in Docker, with correct path forwarding and API keys sent safely in headers.

## Week 2

**Work Done:**

- Built the analytics API: allowed/blocked request totals, hourly traffic buckets for the last 24 hours, and paginated request logs.
- Built the React dashboard: login/signup, API registration, API list and detail pages, a Recharts traffic chart and a request log table.
- Fixed a chart bug where an hour could appear twice (25 buckets instead of 24) by anchoring the time window at the current hour and generating exactly 24 buckets.
- Added `AnalyticsServiceTest`, which checks for exactly 24 distinct hourly labels at seven different times of day, because the bug only appeared at certain times.
- Found that browser clients could not call the gateway because `X-Api-Key` was missing from the CORS allowed headers (`curl` tests never exercised CORS); documented the gap and the planned fix.
- Fixed a blank page on reload of `/apis/{id}` caused by the Vite proxy key `/api` also matching `/apis`; changed the key to `/api/`.

**Outcome:**

The analytics dashboard showed live traffic data from the backend, with correct hourly charts, working page reloads and a documented plan for the CORS gap.

## Week 3

**Work Done:**

- Fixed the browser's native "Sign in" popup that appeared for unauthenticated requests: Spring Security still sent `WWW-Authenticate: Basic` even with HTTP Basic disabled, so an explicit authentication entry point now returns a bare 401.
- Found the same popup coming from a second code path (requests with an invalid or expired JWT) and fixed it by adding an explicit failure handler to the JWT authentication filter.
- Added tests for both failure paths (no token, and an invalid token), each asserting that `WWW-Authenticate` is not present.
- Traced intermittent CORS/403 failures during login testing to several Vite dev servers running at once, which pushed the frontend to port 5174 (not in the CORS allowlist).
- Cleared the stale processes and set a team rule that only one dev server runs at a time.

**Outcome:**

Expired or missing sessions now behave consistently without browser popups, both authentication failure paths are covered by tests, and local testing is reproducible.

## Week 4

**Work Done:**

- Moved the dashboard onto the consolidated backend: the gateway became a Spring Web MVC controller that looks up each registered API in PostgreSQL, and the dashboard became a single static page served by Spring Boot, so the system ships as one container.
- Switched dashboard data to database-side aggregation (allowed/blocked per API, hourly traffic, p50/p95 latency) so raw logs are never sent to the browser.
- Fixed expired sessions returning 403 instead of 401 after the move to the servlet stack, which stopped the dashboard from logging users out; set `HttpStatusEntryPoint(UNAUTHORIZED)` and re-tested both the no-token and invalid-token paths.
- Updated CORS to allow the gateway's request headers (closing the Week 2 gap) and expose `Retry-After`, so browser code can read how long to wait after a 429.
- Fixed the request log filter crashing when no date was selected (PostgreSQL "could not determine data type of parameter"); empty dates are now replaced with fixed minimum and maximum values.
- Added `RequestLogRepositoryFilterTest`, which runs against a real PostgreSQL container and covers the outcome, client and date filters, plus a check that one API's logs never appear under another API.

**Outcome:**

The dashboard runs on the final backend with server-side aggregation, correct logout on expired sessions, browser-readable rate-limit headers and a working, tested log filter.

## Week 5

**Work Done:**

- Built the dashboard's Test lab, which sends a chosen number of concurrent requests to a gateway URL from the browser and reports admitted, blocked and deviation from the limit against the ±2% target, plus a token bucket vs sliding window comparison.
- Built the System page, showing Redis health, the fail-open/fail-closed setting and p50/p95 gateway-added latency.
- Fixed the Test lab reporting −100% deviation: it counted only 2xx responses as admitted, so a target's 404s looked like gateway rejections. Every non-429 response now counts as admitted, and target errors are shown separately.
- Fixed the browser silently following redirects from the target (bypassing the gateway and failing on CORS) by using `redirect: 'manual'` in the Test lab.
- Found during live testing on Render that one client was getting several budgets because Cloudflare edge IPs were used as the client identity; the gateway now reads `CF-Connecting-IP` when configured, and is off by default so the header cannot be spoofed locally.
- Re-ran the Test lab on the live site and confirmed 0% deviation, with one consistent client IP in the request log.

**Outcome:**

The dashboard can measure enforcement accuracy and system health directly, the measurements are correct, and rate limiting works correctly on the live Cloudflare-fronted deployment.
